## 3. 핵심 알고리즘 (이 앱이 어려운 이유)

### 3.1 도시 순서 + 날짜 배분 + 수단 선택 (F3)
- **문제 성격:** 출발 날짜에 따라 비용이 바뀌는 순회 문제(시간 의존 TSP)에 체류 일수 선택이 더해진 형태다.
- **완전 탐색의 크기:** 도시 n개면 순서만 n!이고, 각 도시의 체류 일수 조합과 구간별 수단 선택이 곱해진다.
- **방법:** 상태 = (방문한 도시 집합, 현재 도시, 현재 날짜)인 동적 계획법을 쓴다. Held-Karp 방식의 시간 의존 확장이다.
  - 계산량은 대략 2ⁿ × n² × (날짜 수) × (체류 선택지 수)다.
  - n = 8, 날짜 30일 정도면 브라우저에서 돌릴 수 있는 규모로 추정한다. 실제 시간은 측정으로 확정한다.
- **상위 K개 대안:** 각 상태에 최선 1개 대신 K개를 유지하는 K-best 동적 계획법을 쓴다.
- **가성비 모드:** 목적 함수 = 비용 + λ × 이동 시간이다. λ는 사용자가 슬라이더로 정한다.

### 3.2 하루 일정 (F7)
- 시간창이 있는 오리엔티어링 문제다. 모든 곳을 다 갈 수 없을 때 무엇을 빼고 어떤 순서로 갈지를 정한다.
- 장소가 적으면 정확해(완전 탐색)를 구하고, 많으면 휴리스틱(삽입 + 2-opt)을 쓴다.
- 휴리스틱 결과가 정확해보다 얼마나 나쁜지(최적 격차)를 시험으로 측정해 보고한다.

## 4. 아키텍처

```text
┌──────────────────────── 브라우저 (정적 배포, 서버 없음) ─────────────────────────┐
│  UI: React + TypeScript                                                         │
│   입력 폼 ─ CSV 붙여넣기 ─ 결과 타임라인 ─ 비용 분해 ─ 지도(OpenStreetMap)         │
│        │ postMessage                                                           │
│  Web Worker ──▶ 최적화 엔진 (C++17 → WebAssembly, Emscripten)                   │
│                  · 도시 순서 DP, K-best · 하루 일정 휴리스틱                       │
│  데이터 어댑터: ExampleProvider │ CsvProvider │ (Could) LiveProvider              │
└────────────────────────────────────────────────────────────────────────────────┘
 같은 엔진 소스를 네이티브로도 빌드 → 정확성·성능 시험은 네이티브와 WASM 양쪽에서
```

| 결정 (ADR 후보) | 선택 | 이유 |
|---|---|---|
| ADR-1 엔진 언어 | C++ → WASM | 계산량이 크고, 다음 프로젝트(트레이스 뷰어)와 같은 툴체인을 연습할 수 있음. 대안: TypeScript(단순하지만 연습 효과 없음) |
| ADR-2 서버 유무 | 정적 배포, 서버 없음 | 운영 비용 0을 목표로 하고 개인정보를 서버에 두지 않음. 공유는 URL 인코딩으로 |
| ADR-3 엔진 실행 위치 | Web Worker | 계산 중 화면이 멈추지 않게 |
| ADR-4 가격 데이터 | 어댑터 인터페이스 + 수동/CSV 우선 | 실시간 항공권 API의 공개 제공 여부·약관·비용이 확인되지 않음. 엔진과 UI는 데이터 출처와 무관하게 완성 |

1. 주 대상 지역: 유럽, 일본, 국내 등. 기차 데이터와 지도 범위가 달라진다.

4. 실시간 가격 데이터를 쓸 생각이면, 후보 API의 공개 제공 여부·약관·비용을 먼저 확인
