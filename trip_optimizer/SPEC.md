## 3. 핵심 알고리즘

### 3.1 데이터 모델
- **노드:** 0 = 출발 도시, 1..V = 방문 도시(각 정확히 한 번), V+1 = 귀국 도시. 출발과 귀국이 같은 도시여도 엔진에서는 별개 노드로 다룬다.
- **날짜:** 계획 기간을 0..D−1의 정수 인덱스로 다룬다. 실제 날짜 변환은 UI가 맡는다.
- **이동 구간:** `price[a][b][day][mode]`, `minutes[a][b][day][mode]`. 가격이 음수면 그 선택지가 없다는 뜻이다.
  - 한 구간은 출발한 날 도착한다고 가정한다(야간 이동은 범위 밖).
- **체류:** 도시 i에 day t에 도착해 s박 하면 day t+s에 떠난다.
  - s는 [stay_min_i, stay_max_i] 범위이고, t+s ≤ D−1이어야 한다.
  - 숙박비는 `lodging[i][t] + … + lodging[i][t+s−1]`이다.
- **목적 함수:** 구간 가격 합 + 숙박비 합 + (분당 시간 가치) × 이동 시간 합.
  - 모든 금액과 시간은 **정수(원, 분)**로 계산한다. 그래서 결과가 플랫폼과 무관하게 정확히 같다.
  - UI의 "1시간의 가치(원)"는 분 단위로 반올림해 엔진에 넘기고, 실제로 쓴 값을 화면에 표시한다.

### 3.2 도시 순서 + 박수 + 수단 + 출발일 (F3)
- **방법:** 상태 = (방문한 도시 집합, 현재 도시, 도착일)인 동적 계획법이다. Held-Karp 방식의 시간 의존 확장이다.
- **계산량:** 약 2^V × V² × D × (박수 선택지) × (수단 수)다. V = 8, D = 30, 박수 1~4, 수단 3이면 브라우저에서 처리 가능한 규모로 추정하고, 실제 시간은 측정으로 확정한다.
- **상위 K개(F4):** 각 상태에 최선 1개 대신 K개를 유지한다(K-best 동적 계획법). 비용이 더해지기만 하므로, 상태마다 상위 K개만 남겨도 전체 상위 K개가 보존된다.
- **동점 처리:** 같은 비용이면 생성 경로의 결정적 순서로 정렬한다. 같은 입력이면 항상 같은 순서로 결과를 낸다.
- **한도:** 방문 도시 10개까지. 상태 표가 2^V에 비례해 커지기 때문이다.

### 3.3 하루 일정 (F8)
- 시간창이 있는 오리엔티어링 문제다. 모든 곳을 다 갈 수 없을 때 무엇을 빼고 어떤 순서로 갈지를 정한다.
- 장소가 적으면 정확해(완전 탐색)를, 많으면 휴리스틱(삽입 + 2-opt)을 쓴다.
- 휴리스틱 결과와 정확해의 격차를 시험으로 측정해 보고한다.

## 4. 아키텍처

```text
┌──────────────────── 브라우저 (정적 배포, 서버 없음) ────────────────────┐
│  UI ── 입력 폼, CSV 붙여넣기, 결과 타임라인, 비용 분해, 공유 링크         │
│   │   model 모듈 (순수 JS): CSV 파싱 → 엔진 배열 구성 → 결과 해석          │
│   │ postMessage                                                         │
│  Web Worker (module) ──▶ engine.mjs + engine.wasm (C++17, Emscripten)    │
└──────────────────────────────────────────────────────────────────────────┘
 같은 엔진 소스를 네이티브로도 빌드 → 정확성 시험은 네이티브, 동등성 시험은 네이티브↔WASM
```

### 4.1 엔진 C 인터페이스 (JS ↔ WASM 경계)
- 입력은 3.1절 배열을 **평탄화한 숫자 배열**로 넘긴다. 인덱스는 `((a × N + b) × D + day) × M + mode`이고, N = V + 2다. JSON 파서가 필요 없다.
- 금액·시간은 JS 숫자와 맞추기 위해 `double`로 받는다. 정수이고 2^53 미만인지 엔진이 검사한다.
- 출력도 평탄화한 배열이다. 계획마다 아래 순서로 나열한다.
  - 목적값, 교통비, 숙박비, 이동 분
  - 구간 수, 구간 × (출발, 도착, 날짜, 수단, 가격, 분)
  - 체류 수, 체류 × (도시, 도착일, 박수, 숙박비)
- 반환값: 계획 수(0 = 가능한 여행 없음), −1 = 입력 오류(오류 문자열 함수로 조회), −2 = 출력 버퍼 부족.
- **WASM 빌드는 기본적으로 C++ 예외를 잡지 못한다.** 그래서 경계 함수는 예외를 쓰지 않고 입력을 먼저 검증해 오류 코드로 돌려준다.
- Emscripten 옵션: `MODULARIZE`, `EXPORT_ES6`, `ALLOW_MEMORY_GROWTH`, `ENVIRONMENT=web,worker,node`. 메모리가 늘면 HEAP 뷰가 바뀌므로 호출 후에 매번 다시 읽는다.

### 4.2 아키텍처 결정 (ADR)

| ADR | 결정 | 이유 / 대안 |
|---|---|---|
| ADR-1 엔진 언어 | C++17 → WASM | 계산량이 크고, 다음 프로젝트와 같은 툴체인 연습. 대안 TypeScript는 단순하지만 연습 효과가 없음 |
| ADR-2 서버 유무 | 정적 배포, 서버 없음 | 운영비 0, 개인정보를 서버에 두지 않음. 공유는 URL 해시 |
| ADR-3 엔진 실행 위치 | Web Worker | 계산 중 화면이 멈추지 않게 |
| ADR-4 가격 데이터 | 어댑터 + CSV·예시 우선 | 실시간 항공권 API의 공개 제공 여부·약관·비용 미확인. 엔진과 UI는 데이터 출처와 무관하게 완성 |
| ADR-5 UI 구현 | **결정 필요:** (a) 빌드 단계 없는 순수 JS 모듈 (b) React + TypeScript | (a)는 의존성이 없어 어디서나 검증 가능하고 걷는 뼈대에 적합. (b)는 채용 시장 기술 스택 증거. 추천은 1~2주차 (a), 3주차 이후 (b)로 이행 |

### 4.3 입력 형식 (F2)
- 방문 도시: 한 줄에 `도시,최소박,최대박`
- 이동 구간 CSV: `출발도시,도착도시,날짜(YYYY-MM-DD),수단,가격(원),소요분`
- 숙박 CSV(선택): `도시,날짜,1박가격(원)`. 없으면 0으로 계산하고 화면에 "숙박비 미포함"이라고 표시한다.
- 규칙:
  - 알 수 없는 도시 이름은 줄 번호와 함께 오류를 낸다.
  - 계획 기간 밖의 날짜 줄은 건너뛰고 몇 줄인지 알린다.
  - 수단 이름은 등장 순서대로 번호를 매긴다.

## 6. 배포·DevOps

### 6.1 호스팅
- **GitHub Pages.** 저장소가 공개 상태라 무료로 쓸 수 있다(2026-10-08 확인).
- **저장소 설정 필요:** Settings → Pages → Source를 "GitHub Actions"로 바꾸는 작업은 저장소 소유자가 직접 해야 한다.
- **배포 브랜치:** Pages 배포 환경은 기본적으로 기본 브랜치(`main`)에서만 배포를 허용한다. 작업 브랜치는 빌드·시험만 하고, 배포는 `main` 병합 시 실행한다.

### 6.3 개발 환경 제약
- 이 저장소의 클라우드 세션 환경에서는 npm 레지스트리와 Emscripten 배포 서버에 접근이 막혀 있다(2026-10-08 확인). 그래서 WASM 빌드, npm 의존성, Playwright는 **CI에서만 검증**하고 결과를 CI 로그로 확인한다.
- 환경의 네트워크 설정에서 패키지 매니저를 허용하면 로컬에서도 검증할 수 있다.
- 네이티브 엔진과 순수 JS 모듈(V1~V3, V6)은 로컬에서도 검증할 수 있다.

## 8. 확인이 필요한 것

1. **Pages 설정:** Source를 "GitHub Actions"로 바꾸고, 배포는 `main` 병합으로 할지, 작업 브랜치 배포를 허용할지
