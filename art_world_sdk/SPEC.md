## 0. 용어: 이것 전체가 SDK는 아니다

이 문서가 다루는 것은 **창작 플랫폼**이고, SDK는 그중 개발자용 계층이다.

| 계층 | 정체 | 사용자 | 이 문서의 항목 |
|---|---|---|---|
| SDK | 세계관 형식, 스타일 축, 생성기 플러그인 규약, Python·JS API, 적합성 시험 키트, CLI | 개발자, 크리에이티브 코더 (U1, U3) | W, X, K, G, R, C, T-03 |
| 엔진 | 실제로 그리고 소리 내고 움직이는 구현체 (render3d, 사운드 합성기, 인터랙션 런타임) | SDK가 호출 | M, 4.1절 |
| 앱 | 대화형 스튜디오(대화창 + 시안 비교 보드 + 해석 패널 + 버전 타임라인), 세계관 직접 편집 모드 | 작가 (U2) | A, T, D |
| 에이전트 | 작가의 말을 해석해 SDK를 호출하는 대화 계층. 처음 보는 요구는 처리 경로(N)를 탐색 | 작가 (대화로) | A, N, CT |
| 경험 런타임 | 관객이 웹에서 들어가 걷고 만지고 대화하는 실시간 3D 세계 | 관객 | XR, CH |

- 비슷한 구조의 예: 게임 엔진은 엔진 + 편집기 앱 + 스크립트 SDK, Blender는 앱 + Python API, p5.js는 창작 코딩 라이브러리다.
- 이 프로젝트의 원칙: **앱은 SDK의 공개 API만으로 만든다.** 앱이 SDK의 첫 번째 사용자이자 SDK 설계의 검증 수단이다.
- 이름: 플랫폼 전체는 가칭 "World Platform", 개발자용 계층이 "World SDK"다.

## 1-A. 다섯 재료 모델

어떤 요구든 아래 다섯 재료의 조합으로 바꾼다. 바뀌는 것은 조합이고, 플랫폼 구조는 바뀌지 않는다.

| 재료 | 뜻 | 예 |
|---|---|---|
| 개념 (Concept) | 철학, 건축 이론, 다른 작가의 사상 같은 추상적 생각. 출처와 함께 | 모듈러(인체 비례 체계), 접힘, 여백 |
| 세계 (World) | 개념이 규칙이 된 것: 미학, 서사, 물리 법칙 | 중력이 절반인 신세계, 모든 치수가 모듈러를 따르는 도시 |
| 몸 (Body) | 존재하고 움직이는 모든 것: 관절, 재질, 능력 | 휴머노이드, 로봇 팔, 숨 쉬는 건물, 입자 떼 |
| 행동 (Behavior) | 몸이 시간에 따라 하는 일 | 걷기, 그리기, 말하기, 관객에게 반응 |
| 표현 (Expression) | 결과가 세상에 나오는 방식 | 웹 3D 세계(기본), 이미지, 소리, 음성, 영상, 실제 로봇, 인쇄물 |

| 요구 예 | 개념 | 세계 | 몸 | 행동 | 표현 |
|---|---|---|---|---|---|
| 철학자의 개념을 로보틱스로 | 철학 개념 카드 | 개념에서 나온 규칙 | 로봇 | 규칙을 따르는 움직임 | 웹 3D, (선택) 실제 로봇 |
| 자연어로 말하는 3D 로봇 | 캐릭터의 철학 | 세계의 서사 | 3D 로봇 | 관객과 대화하며 몸짓 | 웹 3D + 음성 |
| 관절을 움직이며 그림 그리기 | "펜을 떼지 않는다" | 획 규칙 | 로봇 팔 | 획 → 관절 궤적 | 그려지는 과정 + 완성 그림 |
| 신세계 | 작가의 상상 | 새 물리 법칙, 생태 | 그 세계의 존재들 | 생태계의 움직임 | 탐험 가능한 웹 3D |

## 1. 설계 원칙

| # | 원칙 | 뜻 |
|---|---|---|
| P1 | 미학은 코드가 아니라 데이터에 | 시스템 코드에 특정 스타일이 없다. 스타일별 함수 금지. 모든 미적 선택은 세계관 데이터에 |
| P2 | 스타일은 축으로 | "미니멀 ↔ 화려함"은 여러 축(밀도, 색, 형태, 질감, 소리, 움직임, 서사)의 조합. 축은 확장 가능 |
| P3 | 섞고, 갈래 내고, 변형한다 | 세계관 합성(비율), 복제 후 수정(관계 기록), 시간에 따른 변형 경로 |
| P4 | 생성 방식도 스펙트럼 | 절차적(정확·통제), AI(풍부·의외), 혼합, 작가 직접 입력을 상황에 맞게 |
| P5 | 모든 단계에 탈출구 | 결과 직접 수정, 자기 에셋 가져오기, 규칙 깨기, 코드로 대체 |
| P6 | 매체는 플러그인 | 새 매체를 추가해도 핵심 코드는 바뀌지 않는다 |
| P7 | 작가가 소유하고 통제 | 세계관·학습 데이터는 작가 소유, 기본 비공개. 생존 작가 화풍 모방 기능은 기본 제공하지 않음 |
| P8 | 모순은 평균하지 않는다 | 서로 반대되는 세계(아이·어른, 중세·현대)를 섞을 때 기본값은 둘이 각자 알아볼 수 있게 남는 결합이다. 평균은 둘 다 흐려지므로 선택 사항이다 |

|---|---|---|
| W-01 | 세계관은 구조화된 문서다: 시각 언어, 존재(캐릭터·사물), 장소, 서사, 소리, 움직임, 금지 목록, 참고 자료 | Must |
| W-02 | 모든 영역은 선택 사항이다. 빈 세계관도 유효하다 (미니멀한 세계관은 적게 쓴다) | Must |

### K. 모순 결합 (서로 반대되는 세계를 합치기)

두 세계를 50:50으로 섞으면 대개 둘 다 흐려진 애매한 결과가 나온다.
그래서 **결합 방식**을 고를 수 있게 하고, 속성마다 다른 방식을 쓸 수 있게 한다.

| 결합 방식 | 뜻 | 예 |
|---|---|---|
| 병치 | 두 세계가 온전한 채로 같은 공간에 나란히 | 중세 성벽 앞에 현대 네온 간판 |
| 혼종 | 속성마다 출처를 고른다 (형태는 A, 재질은 B) | 고딕 아치 형태 + 크롬 재질 / 아이의 비례 + 어른의 주제 |
| 층위 | 스케일이나 층마다 다른 세계 | 큰 구조는 중세, 세부 장식은 현대 |
| 시점 | 보는 사람에 따라 다른 세계 | 아이 눈높이(약 1.1 m)에서는 동화, 어른 눈높이(약 1.7 m)에서는 기계 도시 |
| 시간 | 시간이 흐르며 한 세계에서 다른 세계로 | 관객이 머무를수록 중세가 현대로 바뀐다 |
| 경계 | 두 세계가 만나는 이음매를 따로 디자인 | 석재가 금속으로 녹아드는 경계면 |
| 평균 | 수치를 비율로 섞음 | 선택 사항 (기본값 아님) |

| ID | 요구사항 | 우선순위 |
|---|---|---|
| K-01 | 두 개 이상의 세계관을 결합한 세계관을 만들 수 있고, 원본 세계관과의 관계가 기록된다 | Must |
| K-02 | 결합 방식을 속성(형태, 재질, 색, 비례, 주제, 소리, 움직임)마다 따로 지정할 수 있다 | Must |
| K-03 | "대립 쌍"(예: 아이 ↔ 어른, 중세 ↔ 현대)을 선언하고, 각 쌍에 어떤 결합 방식을 쓸지 정할 수 있다 | Should |
| K-04 | 시점 결합: 카메라 높이·위치에 따라 다른 세계관을 적용 | Should |
| K-05 | 시간 결합: 축 값의 변형 경로(X-04)로 한 세계에서 다른 세계로 이동 | Could |
| K-06 | 결합 결과에서 **각 원본 세계를 여전히 알아볼 수 있는지** 지표로 보인다 (V-09) | Should |

### A. 대화 에이전트와 대화형 스튜디오

| ID | 요구사항 | 우선순위 |
|---|---|---|
| A-01 | 작가는 자연어(한국어)와 이미지(참고 사진, 작품, 스케치)로 요청하고, 에이전트가 SDK 도구를 호출한다 | Must |
| A-02 | **해석을 숨기지 않는다:** 변경 전에 "이렇게 이해했다"를 보여 주고, 작가가 말이나 슬라이더로 고칠 수 있다 | Must |
| A-03 | 모호한 요청에는 질문보다 해석이 다른 시안 2~3개로 답한다 | Should |
| A-04 | 작가별 어휘 사전: 해석을 고칠 때마다 그 작가의 단어 뜻을 기록한다 (작가 소유, 비공개) | Should |
| A-05 | 모든 변경은 버전으로 남고 "아까가 나았어" 같은 되돌리기를 대화로 처리한다 | Must |
| A-06 | 비용이 크거나 되돌리기 어려운 작업(고해상도 렌더, 삭제, 외부 공개, 실제 장치 구동)은 작가 승인이 필요하다 | Must |
| A-07 | 처리하지 못하는 요청은 못 한다고 말하고 대안을 제시한다. 비슷한 다른 것으로 바꿔치기하지 않는다 | Must |

**SDK의 에이전트 친화 설계:** 모든 조작은 작은 도구 단위로 노출하고, 입력은 엄격한 스키마로 정의하고 SDK가 다시 검증한다(에이전트가 만든 잘못된 값의 안전망). 모든 변경은 "무엇이 바뀌었나" 설명을 자동 생성한다. 빠른 저해상도 미리보기와 확정 렌더를 분리한다.

**에이전트 모델:** 1차 후보는 Claude Opus 5.5(`claude-opus-5-5`). 도구 사용, 이미지 입력, 엄격한 도구 스키마를 쓴다. 이 모델은 특정 도구 호출을 강제하는 설정(`tool_choice`의 `any`/`tool`)을 지원하지 않으므로 프롬프트로 안내하도록 설계한다. API 비용은 시범 사용으로 측정한다.

### N. 예상 못 한 요구의 처리 경로

작가는 플랫폼이 예상하지 못한 것을 요구한다. 기능을 미리 다 만들 수 없으므로, 처음 보는 요구가 와도 처리할 **경로**를 둔다.
에이전트는 위에서부터 차례로 시도한다.

| 순서 | 경로 | 예 |
|---|---|---|
| N1 | 기존 기능 | "더 어둡게" → 축 조정 |
| N2 | 기존 기능의 조합 | "음악 박자에 맞춰 조명이 깜빡이게" → 사운드 박자 접점 + 인터랙션 |
| N3 | 에이전트가 새 코드를 샌드박스에서 작성 | "관객 심장 박동에 맞춰 건물이 숨 쉬게" → 새 생성기 작성 |
| N4 | 외부 도구로 넘겼다가 결과를 가져옴 | Blender, 게임 엔진과 glTF·USD로 주고받기 |
| N5 | 못 한다고 말하고 기록 | "만지면 차가워지는 벽" → 화면으로 불가, 물리 장치 대안 제시, 기록부에 남김 |

| ID | 요구사항 | 우선순위 |
|---|---|---|
| N-01 | **핵심은 작게, 나머지는 플러그인:** 핵심에는 세계관, 시간·이벤트, 공간, 버전, 권한, 플러그인 규약만 둔다 | Must |
| N-02 | 데이터 형식은 열어 둔다: 정의되지 않은 필드도 버리지 않고 보존한다 | Must |
| N-03 | 샌드박스: 에이전트가 쓴 코드는 자원 제한, 기본 네트워크 차단, 파일 접근 범위 제한 아래에서 실행 | Must |

### 4.1 3D·공간 엔진: `render3d` (cogito5170/se_new)

**현재 기능** (2026-10-08 저장소 확인)
- JSON 장면 하나에서 2D 평면도, PBR 3D(three.js, 부드러운 그림자, 안개), 인터랙티브 HTML을 만든다.
- 헤드리스 Chromium으로 PNG를 렌더링하고, 카메라 투어 영상(webm)을 녹화한다.
- 경로 따라가기 애니메이션이 있다.
- 면적표를 계산한다.
- 현재안/제안안(asis/tobe) 예제가 있다.
- V&V 체계가 있다: 측정·기준·오차·유효 범위를 문서화한다. 이 스펙의 검증 원칙과 같다.

**이 SDK에 쓰려면 필요한 확장**

| 현재 제약 | 필요한 확장 | 관련 요구사항 |
|---|---|---|
| 객체 종류가 매장 집기 목록으로 고정 (선반, 계산대, 피규어 등) | 객체 종류 등록부: 플러그인이 새 종류를 등록. 일반 도형과 glTF 모델 가져오기 | P6, E-02 |
| 재질·색이 렌더러 코드에 고정 | 재질·팔레트를 세계관 데이터에서 받기 | P1, W-01 |
| 관절이 있는 물체 없음 | 관절 계층과 관절 궤적 애니메이션 | M-07 |
| 소리 없음 | 공간 음향 계층 | M-08 |
| 장면당 세계 하나 | 영역별 세계관, 포털 | M-09, K-01 |

**접근 권한:** 이 세션은 se_new를 **읽기만** 할 수 있다. render3d를 확장하려면 se_new에서 작업하거나 쓰기 권한을 붙여야 한다. 대안은 이 SDK 쪽에 "세계관 → render3d 장면 JSON" 어댑터를 두고, render3d의 확장은 se_new에 따로 제안하는 방식이다. **결정 필요.**

기준 세계관 목록은 인터뷰한 작가들의 실제 세계관으로 교체·보강한다 (작가 동의를 받은 경우).

## 7. 작가 인터뷰 계획

### 7.1 대상
- **"혁주 작업 공간"을 사용하는 작가들.**
- 확인 필요 (TODO):
  - 공간의 성격(작업실, 공유 스튜디오, 메이커스페이스, 온라인 공동체 등)
  - 작가 수
  - 주로 다루는 매체
  - 연락·섭외 방법
- **표본 다양성:** 다양성이 이 시스템의 핵심 목표라서, 스타일이 서로 다른 작가를 고른다. 가능하면 아래를 각 1명 이상 포함한다.
  - 미니멀 계열
  - 화려하거나 장식적인 계열
  - 사운드 또는 인터랙션 작업
  - 3D·공간 작업
- 공간의 작가들이 한쪽 스타일에 몰려 있으면 그 사실을 기록하고, 외부 작가로 보강할지 결정한다.
- 목표 인원: 3~5명.

### 7.2 진행 방식
- 1인 60분 내외, 작업 공간에서 실제 작업물을 보며 진행
- **동의:** 녹음 여부, 작품 사진 사용 여부, 이름 공개 여부를 시작 전에 따로 묻고 기록한다. 기본값은 비공개
- 인터뷰 결과에 작가의 미공개 작품이나 개인 정보를 담지 않는다

### 7.3 질문 가이드
1. **세계관:** 작품 밑에 깔린 "세계"가 있나요? 그걸 지금 어떻게 기록하고 관리하나요? (무드보드, 노트, 레퍼런스 폴더 등)
2. **매체 이동:** 같은 세계를 다른 매체로 옮겨 본 적이 있나요? 어디서 가장 막혔나요?
3. **일관성:** "이건 내 세계에 안 맞는다"고 느끼는 기준은 무엇인가요? 말로 설명할 수 있나요?
4. **도구:** 지금 쓰는 도구와, 그 도구에서 가장 시간을 많이 버리는 일은?
5. **AI:** AI 생성 도구를 써 봤나요? 쓰지 않는다면 이유는? (소유권, 화풍 모방, 결과의 획일성 등)
6. **규칙과 파괴:** 자기 세계관의 규칙을 일부러 깨는 경우가 있나요?
7. **협업과 공유:** 세계관을 다른 사람과 공유하거나 함께 만들어 본 적이 있나요?
8. **말로 설명하기:** 작업을 조수나 협업자에게 말로 설명할 때 어떤 단어를 쓰나요? (에이전트 평가 세트 V-13의 원재료)
9. **해 보고 싶었지만 못 한 것:** 도구가 없어서, 기술을 몰라서, 비용 때문에 포기한 작업이 있나요? (예상 못 한 요구 세트 V-12의 원재료)

### 7.4 관찰 과제
- 4절의 세계관 형식 초안을 보여 주고, 작가 본인의 세계관 일부를 이 형식으로 옮겨 보게 한다.
- 옮길 수 없었던 것, 형식이 강요한 것, 빠진 영역을 기록한다. **이것이 W·X 요구사항을 고치는 가장 직접적인 근거다.**

### 7.5 숨겨 둔 요구 세트 봉인
- 인터뷰에서 나온 요구(특히 질문 9)와 작가에게 받은 엉뚱한 요구를 모은다.
- 그중 무작위로 일부를 **개발 중에 보지 않을 시험 세트**로 따로 봉인한다. 개발에는 나머지만 쓴다.
- 단계 5와 6에서 봉인을 풀어 V-12로 측정한다.

### 7.6 분석과 반영
- 인터뷰마다 요약(동의 범위 안에서)을 남기고, 공통 주제를 묶는다.
- 요구사항 변경은 "어느 인터뷰의 어떤 관찰 때문에"를 함께 기록한다.
- 인터뷰로 뒷받침되지 않은 요구사항은 Could로 내린다.

| 작가들의 AI 거부감 | 작가 소유·비공개 기본(R-04), 생존 작가 모방 기능 미제공(P7), AI 없이 절차적 생성만으로도 쓸 수 있게 |
| 인터뷰 표본이 한 공간에 몰림 | 7.1의 다양성 확인, 필요 시 외부 보강 |
| 에이전트가 작가 의도를 평균적인 취향으로 끌고 감 | 해석 공개(A-02), 시안으로 묻기(A-03), 작가별 어휘 사전(A-04) |

| "모든 요구"로 범위가 무한히 커짐 | 다섯 재료 + 처리 경로로 일반성을 확보하고, 첫 결과물은 그림 그리는 로봇 하나로 좁힘 |
