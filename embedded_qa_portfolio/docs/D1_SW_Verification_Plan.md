# D1. SW Verification Plan — BMS 펌웨어 (초안 v0.1)

> 근거 요건: [A10, A11, A14]. 상태: 2주차 초안이며, 12주차에 실제 결과로 갱신한다.
> 이 계획은 ASPICE SWE.4(단위 검증)·SWE.5(통합 시험)·SWE.6(SW 적격성 시험)의 **개념을 적용**해
> 시험 레벨을 나눈 것이다. ASPICE 평가나 준수를 뜻하지 않는다.

## 1. 목적과 범위

| 항목 | 내용 |
|---|---|
| 대상 | `firmware/`의 BMS 애플리케이션 계층(하드웨어 독립 C 코드). HAL은 SIL용 호스트 구현만 해당 |
| 기준 문서 | `requirements/swr.yaml`(SWR), `requirements/safety_goals.yaml`(SG·FN), `can/bms.dbc`, `docs/D3_HARA_lite.md` |
| 목표 | 모든 SWR이 정해진 방법(test/analysis/review)으로 검증되었음을 추적 가능한 증거로 보인다 |
| 범위 밖 | 실제 하드웨어 전기 특성, MCU 실시간 성능(키트를 사지 않으면), 셀·컨택터 하드웨어, Cybersecurity |

## 2. 시험 레벨

| 레벨 | ASPICE 개념 | 대상 | 환경 | 도구 | 판정 기준 |
|---|---|---|---|---|---|
| L1 단위 검증 | SWE.4 | `app/` 모듈 함수 | 호스트 빌드 | Unity, gcov, cppcheck, clang-tidy | 단위 시험 전부 통과, 커버리지 기준 충족, 정적 분석 error 0 |
| L2 통합 시험 | SWE.5 | 펌웨어 전체 + CAN·UDS 인터페이스 | SIL 리그(플랜트 모델 폐루프) | pytest, python-can, cantools, udsoncan | 인터페이스(DBC 주기·형식, UDS 응답) 시험 전부 통과 |
| L3 SW 적격성 시험 | SWE.6 | SWR 전체(블랙박스) | SIL 리그, (선택) 실버스 리그 | pytest, 결함 주입 API | `method: test`인 SWR 100%가 통과 TC를 가짐 |

**레벨을 나눈 이유:** L1은 빠르고 결정적이라 커밋마다 돈다. L2·L3는 플랜트 모델과 시간 축이 필요해 시나리오 단위로 돈다. 같은 SWR을 L1과 L3에서 모두 검증할 수 있지만, 판정의 근거가 되는 기록은 L3를 우선한다(블랙박스 관점).

## 3. 검증 방법 배정

| `method` | 의미 | 증거 |
|---|---|---|
| test | 시험으로 검증 | TC 실행 기록(`evidence/<TC-ID>/`), CI 실행 ID |
| analysis | 분석으로 검증 (예: SWR-028 동적 메모리 미사용) | 정적 분석·심볼 검사 결과 |
| review | 검토로 검증 | 검토 기록(`docs/review_log.md`) |

현재 배정: test 31개, analysis 1개 (`python tools/req_check.py`로 집계).

## 4. 시험 환경

| 환경 | 구성 | 상태 |
|---|---|---|
| E1 호스트 빌드 | `ci/Dockerfile` 이미지: gcc, CMake, gcov, ARM 크로스 컴파일러 | 2주차 구축, CI 녹색 |
| E2 SIL 리그 | 펌웨어 공유 라이브러리 + Python 플랜트 모델 + 가상 CAN 버스, 1 ms lockstep | 완료 |
| E3 실버스 리그 | STM32 보드 + USB-CAN 어댑터 (모델 TODO) | 8주차 관문에서 결정 |

환경의 한계는 결과 리포트에 함께 적는다. 특히 SIL의 시간은 시뮬레이션 시간이고, MCU 실행 시간이 아니다.

## 5. 진입·종료 기준

| 레벨 | 진입 기준 | 종료 기준 |
|---|---|---|
| L1 | 요구사항 품질 검사 통과, 빌드 경고 0 | 단위 시험 전부 통과, `app/` 라인 커버리지 90% 이상·분기 80% 이상, cppcheck error 0, 모든 정적 분석 일탈에 사유 기록 |
| L2 | L1 종료, DBC 검사 통과, SIL 리그 상태 점검 통과 | DBC 송신 메시지 전부의 주기 시험 통과, UDS 구현 서비스마다 긍정·부정 응답 시험 통과 |
| L3 | L2 종료 | `method: test` SWR 100%에 통과 TC 연결, 미해결 결함 중 severity high 이상 0건, 판정 보류(요구사항 모호) 항목 목록화 |

## 6. 결함 관리

1. 실패한 시험은 곧바로 결함으로 보지 않는다. 먼저 한 번 재실행하고 다음 중 하나로 분류한다.
   - **제품 결함:** 펌웨어가 요구사항을 어김
   - **시험 결함:** TC나 시험 도구가 틀림
   - **환경 문제:** 리그·플랜트 모델·CI 인프라 문제
   - **요구사항 모호:** 요구사항이 판정 기준을 주지 않음
2. 제품 결함은 결함 로그에 ID(BUG-NNN), 재현 절차, 기대·실제, 증거 경로, 심각도와 함께 남긴다.
3. 결함을 고치면 그 결함을 잡는 회귀 시험이 있어야 닫을 수 있다.
4. 시험 결함과 환경 문제도 기록한다. 1주차에 요구사항 검사기 자체의 결함을 찾은 사례(`docs/review_log.md` RV-W1-01)처럼, 검증 도구도 검증 대상이다.
5. 프로젝트 중 실제로 발견한 제품 결함 1건 이상으로 8D 리포트(D7)를 쓴다. 발견된 결함이 없으면 쓰지 않고 그렇게 기록한다.

## 7. 추적성

- **요구사항 → 시험:** 모든 TC는 검증하는 SWR ID를 태그로 단다. 단위 시험은 C 주석 `@verifies SWR-NNN`, SIL 시험은 pytest 데코레이터로 단다(D2 참고).
- **안전 목표 → 요구사항:** `swr.yaml`의 `parent` 필드로 연결한다.
- **자동 검사:** CI가 태그의 SWR ID가 실제로 존재하는지, 모든 시험에 태그가 있는지를 검사한다(`tools/tc_tag_check.py`). 7주차에는 양방향 추적 매트릭스를 생성한다(D4).

## 8. 역할과 독립성

1인 프로젝트라서 작성자와 검증자가 같다. ISO 26262가 요구하는 검증 독립성은 확보되지 않는다. 대신 다음으로 일부 보완한다.
- 자동 검사기(요구사항·DBC·태그)를 CI에서 강제한다.
- 검토 체크리스트(D2 5절)로 자기 검토를 한다.
- 기대값은 구현 결과가 아니라 요구사항 문장에서만 도출한다.
