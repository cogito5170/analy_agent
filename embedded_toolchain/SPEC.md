# 임베디드 개발·검증 툴체인 — 스펙 v0.1

> 조합: **Dev 3** (브라우저 CAN 트레이스 뷰어, C++ → WebAssembly) + **Platform 5** (임베디드 테스트 팜 스케줄러)
> + **QA 5** (OTA 중단 지점 전수 결함 주입 하네스).
> 선행 과제: `../trip_optimizer/SPEC.md` (C++ → WASM과 배포 파이프라인 연습).
> 수치 목표는 **첫 측정 후 확정**한다. 측정하지 않은 값은 포트폴리오에 쓰지 않는다.

## 1. 한 줄 요약과 세 과제의 연결

임베디드 팀이 "펌웨어를 바꾸면 → 가상 보드에서 자동으로 돌리고 → 결과를 브라우저에서 바로 들여다보는" 도구 체인을 만든다.
세 과제는 따로 노는 데모가 아니다. 서로의 입력과 출력이 이어진다.

```text
   펌웨어 변경 (BMS, OTA 부트로더)
          │ CI
          ▼
 ┌─────────────────────────────┐   작업 N개 병렬     ┌──────────────────────────────┐
 │ Platform 5: 테스트 팜        │ ─────────────────▶ │ 가상 보드 에이전트 ×N         │
 │  작업 큐 · 보드 대여(lease)  │ ◀───────────────── │  host / Zephyr native_sim /  │
 │  재시도 · 시간 초과 · 지표    │   결과·로그·트레이스 │  QEMU (보드 종류 = 설정)      │
 └──────────────┬──────────────┘                    └──────────────┬───────────────┘
                │ 산출물 저장 (S3 호환 MinIO)                         │ 실행되는 작업의 한 종류
                ▼                                                   ▼
 ┌─────────────────────────────┐                    ┌──────────────────────────────┐
 │ Dev 3: 트레이스 뷰어 (웹)     │ ◀── 링크로 열기 ── │ QA 5: OTA 결함 주입 하네스    │
 │  C++ 디코더 → WASM           │                    │  플래시 시뮬레이터 · A/B 부트  │
 │  DBC 디코딩 · 신호 그래프     │                    │  중단 지점 k마다 작업 1개      │
 │  수백만 프레임 · 공유 링크    │                    │  → 실패 시 트레이스 남김       │
 └─────────────────────────────┘                    └──────────────────────────────┘
```

| 직무 | 이 프로젝트에서의 증거 |
|---|---|
| Dev | 대용량 데이터를 다루는 배포된 웹앱, C++/WASM 성능 최적화 |
| Platform | 공유 자원(보드)을 다루는 스케줄러, 대여·회수 의미론, 가동률 지표 |
| QA | 전수 결함 주입, 시험 하네스 자체의 검증, 차등 시험·퍼징 |
| DevOps (공통) | 모노레포 CI, 컨테이너, PR 미리보기 배포, 산출물 저장·추적 |

## 2. 구성요소

### T. 트레이스 뷰어 (Dev 3)

| ID | 기능 | 우선순위 |
|---|---|---|
| T1 | 입력 형식: candump 로그(can-utils 텍스트), Vector ASC(텍스트, 공개 예제 기준으로 범위 확인 필요), 자체 바이너리 청크 형식(빠른 열기용) | Must (ASC는 Should) |
| T2 | DBC 디코딩: 부호, factor/offset, Intel/Motorola 바이트 순서. 멀티플렉스 신호는 Should | Must |
| T3 | 스트리밍 파싱: Web Worker에서 청크 단위로 파싱하고 시간 색인 생성. 파일 전체를 메모리에 올리지 않음 | Must |
| T4 | 렌더링: 가상 스크롤 프레임 표, 신호 그래프는 화소당 min/max 다운샘플링 | Must |
| T5 | 필터(ID, 신호 값 조건), 검색, 북마크, "파일 + 시간 구간" 공유 링크 | Should |
| T6 | 팜 산출물 URL을 바로 여는 연동 | Must |

**검증**
- **차등 시험:** cantools를 기준(오라클)으로 같은 DBC·프레임을 디코딩해 결과 비교. 불일치 0
- **교차 검증:** 네이티브 빌드와 WASM 빌드 출력 동일
- **퍼징:** 로그 파서와 DBC 파서를 libFuzzer로(네이티브 빌드). 크래시는 전부 회귀 시험으로 고정
- **성능 예산:** Playwright로 실제 브라우저에서 파싱 처리량(MB/s), 첫 화면까지 시간, 메모리 최댓값 측정. 첫 측정 후 예산 고정
- **배포:** 정적 호스팅, PR마다 미리보기

### F. 테스트 팜 스케줄러 (Platform 5)

| ID | 기능 | 우선순위 |
|---|---|---|
| F1 | 보드 종류 = 실행 환경 설정 (host 프로세스, Zephyr native_sim, QEMU 머신). 실보드는 같은 에이전트 인터페이스로 나중에 추가 | Must (QEMU는 Should) |
| F2 | 작업 명세: 펌웨어 산출물, 보드 종류, 시나리오, 시간 제한, 우선순위 | Must |
| F3 | 보드 대여: 한 보드에는 한 작업만, 하트비트가 끊기면 대여 만료 후 회수, 작업 재배정 | Must |
| F4 | 재시도 정책, 취소, 시간 초과 처리. 재시도로 통과한 작업은 "불안정"으로 따로 집계 | Must |
| F5 | 산출물 저장(MinIO), 결과 API, CLI, 간단한 웹 대시보드 | Must |
| F6 | 지표: 보드 가동률, 큐 대기 시간 p50/p95, 대여 만료 횟수, 불안정 작업 비율 | Must |
| F7 | 실패 작업을 QA Agent 방식으로 자동 분류 (제품/시험/환경) | Could |

**검증**
- **불변식 시험:** 가짜 시계와 결정적 시뮬레이션으로 스케줄러를 돌리며 무작위 사건(에이전트 사망, 네트워크 지연, 동시 요청)을 주입
  - 한 보드에 두 작업이 동시에 배정되는 일 0
  - 모든 작업이 완료, 실패, 시간 초과 중 하나로 끝남 (사라지는 작업 0)
  - 죽은 에이전트의 보드는 대여 만료 후 반드시 회수됨
- **카오스:** 실제 컨테이너 에이전트를 작업 도중 강제 종료
- **부하:** 작업 1,000개를 한 번에 넣고 큐 대기 시간과 가동률 측정

### O. OTA 결함 주입 하네스 (QA 5)

| ID | 기능 | 우선순위 |
|---|---|---|
| O1 | 플래시 시뮬레이터(C): 섹터 단위 지우기, 1 → 0 방향 쓰기만 허용, 전원 차단 시 쓰다 만 상태(tearing) 모델, 쓰기 횟수 기록 | Must |
| O2 | 부트로더 + 업데이트 클라이언트(C): A/B 슬롯, 이미지 헤더(버전, 크기, 해시), 서명 검증, 시험 부팅 → 정상 확인 → 확정, anti-rollback 카운터 | Must |
| O3 | 전수 결함 주입: 업데이트 과정의 플래시 연산을 모두 세고, k번째 연산에서 전원 차단 → 재부팅 → 불변식 판정. 쓰다 만 상태 변형 포함 | Must |
| O4 | 불변식: 항상 서명이 유효한 이미지로 부팅된다 / 버전이 anti-rollback 하한 아래로 내려가지 않는다 / 업데이트가 확정됐으면 새 버전이다 | Must |
| O5 | 보안 부정 시험: 변조 이미지, 다른 키 서명, 다운그레이드, 잘린 이미지 | Must |
| O6 | 팜 연동: 중단 지점 k마다 작업 1개로 팜에서 병렬 실행, 결과 행렬, 실패 시 트레이스·플래시 덤프 저장 | Must |
| O7 | Zephyr native_sim·QEMU 타깃에서도 같은 하네스 실행 | Should |

**검증 (하네스 자체를 검증하는 것이 핵심)**
- **전수성:** 열거한 중단 지점 중 실제로 시험한 비율 100%
- **결과:** 정상 구현에서 복구 불가 0, 보안 부정 시험 전부 거부
- **하네스 검증(심은 결함):** 부트로더에 알려진 결함을 하나씩 심고(예: 복사 완료 전에 부트 플래그 기록, 서명 검증 생략, 카운터 갱신 순서 오류), 하네스가 각각을 잡는지 확인한다. 검출률을 보고한다. 하네스가 못 잡는 결함이 있으면 그것이 이 프로젝트의 가장 중요한 발견이다
- **플래시 시뮬레이터 검증:** 시뮬레이터 자체의 시험(지우기 전 0 → 1 쓰기 거부, 쓰다 만 상태 재현)을 먼저 통과시킨다. 시뮬레이터가 틀리면 모든 결과가 거짓 통과가 된다

## 3. 아키텍처 결정 (ADR 후보)

| ADR | 결정할 것 | 1차 제안 |
|---|---|---|
| ADR-1 | 저장소 구조 | 모노레포. 세 구성요소와 공통 스키마(작업 명세, 산출물 메타데이터) |
| ADR-2 | 팜 큐 구현 | PostgreSQL의 `SELECT ... FOR UPDATE SKIP LOCKED` 기반 큐. 대안 Redis·RabbitMQ와 비교해 의존성을 줄이는 쪽 |
| ADR-3 | 팜 서버 언어 | Python(FastAPI). 이미 능숙함. 대안 Go(플랫폼 업계에서 흔함)와의 비교 기록 |
| ADR-4 | 서명 알고리즘·라이브러리 | Ed25519. 작은 C 라이브러리 후보(TweetNaCl, Monocypher 등) 비교 |
| ADR-5 | 트레이스 바이너리 형식 | 청크 + 시간 색인 자체 형식. 대안: 원본 텍스트만 지원 |
| ADR-6 | 플래시 tearing 모델 | 바이트 단위 부분 쓰기 + 마지막 바이트 불확정. 실제 칩 사양과의 차이를 문서화 |

## 4. 단계 (주 20시간 가정, 추정, 여행 앱 5주 이후)

| 단계 | 기간 | 내용 | 관문 |
|---|---|---|---|
| 0 | 2주 | 모노레포, CI, ADR 1~3, C4 컨텍스트 | CI 녹색 |
| 1 | 4주 | **걷는 뼈대:** 팜이 host 보드 에이전트 1개에서 BMS 단위 시험 작업 1개 실행 → 산출물 저장 → 뷰어가 링크로 트레이스 열기 (트레이스는 처음엔 합성 데이터) | 끝-끝 경로가 CI에서 매 커밋 통과 |
| 2 | 6주 | OTA 하네스 핵심 (host): 플래시 시뮬레이터, 부트로더, 중단 지점 열거, 불변식, 심은 결함 검출 | 전수성 100%, 심은 결함 검출률 첫 측정 |
| 3 | 5주 | 팜 강화: 대여·회수, 재시도, 지표, 카오스. OTA 전수 시험을 팜에서 병렬 실행 | 불변식 시험 녹색, 가동률·대기 시간 첫 실측 |
| 4 | 5주 | 뷰어 완성: 형식, DBC 디코딩 차등 시험, 성능 예산, 퍼징 | 차등 시험 불일치 0, 성능 예산 고정 |
| 5 | 3주 | Zephyr native_sim·QEMU 보드 종류, OTA 하네스 이식 | 2개 이상 보드 종류에서 같은 하네스 통과 |
| 6 | 2주 | 직무별 포트폴리오 페이지, 데모 시나리오, 회고 | 모든 주장에 증거 링크 |

합계 약 27주이고, 여행 앱을 포함하면 약 32주다.
필수 경로는 단계 0~3과 6으로 약 19주다. 줄일 때는 5 → 4의 퍼징·ASC → 3의 카오스 순서로 덜어낸다.

## 5. 위험

| 위험 | 대응 |
|---|---|
| 플래시 시뮬레이터가 실제 칩과 달라 거짓 통과 | 시뮬레이터 자체 시험 + 모델과 실제의 차이를 ADR-6에 명시. 실보드가 생기면 같은 하네스로 대조 |
| OTA 단계가 계획보다 길어짐 (가장 어려운 과제) | 단계 2에서 서명·anti-rollback을 뒤로 미루고 A/B + 롤백 전수 시험부터 통과 |
| Zephyr·QEMU 학습 부담 | 단계 5로 미뤄 두고 host 타깃으로 전체 흐름부터 완성 |
| 혼자 만든 하네스를 혼자 검증 | 심은 결함 검출률로 하네스의 능력을 수치로 보임 |

## 6. 기존 작업과의 관계

- **BMS 펌웨어:** 팜의 첫 작업이자 트레이스의 출처
- **`embedded_qa_portfolio/` 빌드 컨테이너·재현성 검사:** 단계 0의 기반
- **QA Agent:** 팜 실패 분류에 재사용 (F7, Could)
- **DBC 검사기의 파싱 경험:** 뷰어의 C++ DBC 디코더로 이어짐
